# pi-career-skills 学习路线图 —— 四步拆解工作流

> 学习者画像：有基础概念的新手（Python 基础即可）。目标岗位：AI 应用开发 / AI Agent 开发工程师。
> 依据：`packages/pi-career-skills` + `packages/pi-agent-core` 当前真实源码（代码、测试、评测记录同步更新）。
> 原则：① 按依赖关系拆解，不按文件结构；② 每个单元 = 可运行最小原型，下一单元使用上一单元的输出；③ 全部练习指向仓库内真实代码与真实测试。

## 第一步：项目全景扫描与前置依赖诊断

### 这个项目的终极价值（一句话）

把一个"会自己上网找职位、排序、改简历、列计划"的 AI 员工，从"演示玩具"变成"能安全上线的生产系统"——它解决的核心痛点是：**LLM 会乱说话、乱调工具、烧钱、死循环，本项目用一套"可信内核"把这些全部兜住。**

### 前置知识清单（5 个核心前置知识点 + 生活化比喻）

| # | 前置知识点 | 生活化比喻 | 需要会到什么程度 |
|---|---|---|---|
| 1 | Python 异步基础（asyncio） | 餐厅点菜：`async def` = 下单；`await` = 等菜但不占桌（别人照常点单）；`asyncio.run()` = 开一个专职送餐员把整桌跑完 | 会 `async def` / `await` / `asyncio.run()`，不必精通事件循环 |
| 2 | LLM 对话 + Function Calling | 和外国同事开会：模型是同事，工具是"查资料的助手"。同事说"帮我查 X"（tool_call），你（循环）去查，把结果贴回会议（tool_result），同事据此继续发言 | 知道模型可以"要求调用工具"并收到结果即可 |
| 3 | 钩子（before / after hook） | 机场安检：进闸口（before_tool_call）查行李（预算、是否重复），出闸口（after_tool_call）盖章（结果要不要进证据库）。业务工具自己不知道安检存在 | 理解"横切关注点"：在调用前后插入逻辑，不改业务代码 |
| 4 | pydantic 模型 + JSON Schema | 海关申报单：模型想调工具必须填标准申报单（input 校验），工具返回也必须符合申报单（output 校验），填错一个字打回重填 | 会读 `BaseModel` 类定义即可，不用会写复杂 schema |
| 5 | pytest 基础 | 入职体检：每次改代码后跑一遍，防止老毛病复发 | 会 `pytest 路径 -q`、能读懂 assert 失败 |

### 核心痛点拆解：三大认知门槛（最容易劝退的地方，提前打预防针）

1. **"模型不可信"完全反直觉**。大多数教程里模型是主角；这里模型是"最不可信的一环"——它说的每句话都要被证据、预算、完成门重新验证。看不懂这一条，就读不懂 controller。
2. **"故意不给模型完整上下文"的取舍**。本项目刻意把工具详情放进 `details`（模型不可见，tool_adapter.py:237-260）、把上下文投影成有界视图（context_projection.py:40）。新手容易觉得"这是功能缺失"，实际是"模型看得越多，编得越离谱"。
3. **多 Agent 之间"传引用、不传值"**。委托边界只传 `ArtifactRef` 句柄（artifact_id / source_url / content_hash），不传业务事实（contracts.py:44-63）。链式评测也已改为通过 `seed_artifacts` 传递有界引用；新手最容易把上游数据整个塞给下游，这是多 Agent 全链崩溃的头号根源。

## 第三步：详细教案（五星教学法，共 7 课）

### 教案单元 1：循环与信封 —— ReAct 是怎么转起来的

**1.【概念锚点】**：整座大楼的"电梯"。模型和工具靠它上下楼，每停一层 = 一轮循环（一个 turn）。

**2.【核心目标】**：能亲手跑通"模型 → 工具 → 模型"；能说出循环结束的 2 种方式。

**3.【原理解读 (Why)】**：没有循环，模型一次只能说一句话，完不成多步任务；没有信封（统一返回结构），工具一报错 exception 就冒泡炸掉整个循环。**不这样做的灾难**：一次网络超时 = 整个 run 报废，而且无法区分"工具失败"和"模型胡说"。

**4.【手把手实操 (How)】**（约 18 行）

```python
# ① 循环骨架（真实代码精简版，pi-agent-core/agent_loop.py:170-215）
while True:                                   # 外层：检查是否还有 follow-up
    has_more_tool_calls = True
    while has_more_tool_calls:                # 内层：ReAct 主循环
        message = await stream(模型)          # ① 模型发言
        tool_calls = [c for c in message.content if isinstance(c, ToolCall)]
        if not tool_calls:                    # ② 没调工具 → 本轮自然结束
            has_more_tool_calls = False
            break
        results = await 执行工具(tool_calls)  # ③ 执行工具
        messages.append(results)              # ④ 结果回填对话，回到 ①
```

```python
# ② 可运行片段：让 faux 模型说一句话（零联网、零 API key）
import asyncio
from pi_ai import Context, UserMessage, stream_simple
from pi_ai.providers.faux import FAUX_MODEL, FauxScript, push_script, clear_scripts

clear_scripts()
push_script(FauxScript(text="收到任务，我来处理。"))   # 预置模型"台词"

async def main():
    ctx = Context(messages=[UserMessage(content="你好")])
    result = await stream_simple(FAUX_MODEL, ctx).result()  # 等最终回复
    print(result.content)

asyncio.run(main())
```

**易错点 + 救命稻草**：
- 忘记 `clear_scripts()`：脚本栈是全局的，上个测试残留的脚本会让输出错乱 → 每次跑前清空。
- `message.content` 里混着普通文本：必须 `isinstance(c, ToolCall)` 过滤，否则把文本当工具调用会报错。
- `stop_reason == "length"`：模型输出被截断时工具参数可能不完整，代码里直接全部判失败（agent_loop.py:207-209）——遇到诡异的参数错误先查这一条。

**5.【刻意练习】**：给内层 `while` 加一个"最多 3 轮"的守卫（数 turn 次数，到 3 就 `break`），然后回答：如果模型一直调工具，这个守卫在第几轮生效？验证：跑通后把守卫删掉，观察 `test_budget_sweep.py` 为什么仍能拦住无限循环（剧透：单元 2 的保险丝）。

### 教案单元 2：保险丝 —— 预算三件套

**1.【概念锚点】**：大楼的"总电闸 + 每层独立电表"。烧钱、死循环全靠它熔断。

**2.【核心目标】**：看懂 `BudgetTracker` / `ToolCallGuard`；能解释"证据换配额"为什么能防死循环。

**3.【原理解读 (Why)】**：LLM 可能无限循环调工具，每一次调用都是真金白银。**不这样做的灾难**：没有预算上限的 agent 上线 = 账户归零 + 卡死整个服务。预算必须挂在循环钩子上（而不是工具里），因为业务工具不该知道预算存在。

**4.【手把手实操 (How)】**（约 16 行）

```python
# ① 架构级硬顶，构造时逐项 clamp，调用方传 99999 也没用（budgets.py:20-27）
HARD_CAPS = {"agent_turns": 100, "tool_calls": 400, "model_requests": 500,
             "input_tokens": 2_000_000, "wall_clock_seconds": 900, "auto_recoveries": 2}

# ② 动态工具配额：真的在产出证据 → 弹药更多（budgets.py:103）
def effective_tool_cap(self, artifact_count: int) -> int:
    grown = self._limits.initial_tool_calls + artifact_count * PER_ARTIFACT_HEADROOM  # +8/件
    return min(HARD_CAPS["tool_calls"], grown)

# ③ 三个钩子各扣一项（agent_hooks.py:52 build_controller_hooks）
#   stream_fn               → 每轮扣 1 turn + 1 model_request
#   should_stop_after_turn  → 扣 input tokens + 查墙钟，超了返回 True 提前终止
#   before_tool_call        → 扣 1 tool_call；重复调用直接 block 不扣预算
```

**易错点 + 救命稻草**：
- 预算必须在钩子扣，不能在工具 handler 里扣——否则换一个业务工具就漏计费。
- 成功过的重复调用**不扣**预算（`guard.is_duplicate`），失败过的重试**要扣**——别把顺序搞反，否则重试会免费无限刷。
- stall 计数：没产出 artifact 的调用 +1，有产出归零；6 次软停（steer 一句中文收尾）、9 次硬停（raise `NO_PROGRESS`，budgets.py:305-339）。

**5.【刻意练习】**：把 `PER_ARTIFACT_HEADROOM` 从 8 改成 16，跑 `test_budget_sweep.py`。回答：为什么配额更大时，"原地打转"的 agent 反而死得更快？（提示：它撞的是 tool_calls 硬顶 400，不是初始配额。）

### 教案单元 3：可信记忆 —— EvidenceStore

**1.【概念锚点】**：大楼的"档案室 + 质检员"。不是所有工具输出都能进档案室，只有盖章合格的证据能存。

**2.【核心目标】**：能说出入库的"三道闸 + 质量门"；能解释"空匹配报告 ≠ 没跑匹配器"。

**3.【原理解读 (Why)】**：模型说"我找到了"不算数——没有质检，垃圾证据会污染下游所有决策（匹配、简历、计划全基于它）。**不这样做的灾难**：一条假职位进库，后面所有环节都基于假数据产出，而完成门还判它"成功"。

**4.【手把手实操 (How)】**（约 15 行）

```python
# add_observation：证据库唯一写入口，三道闸（evidence.py:314-376）
def add_observation(self, obs: ToolObservation) -> list[Artifact]:
    if obs.status != "succeeded":            # 闸1：失败/阻塞的观察不入库
        return []
    artifact_type = TOOL_ARTIFACT_TYPE.get(obs.tool_name)
    if artifact_type is None:                # 闸2：工具必须映射到 artifact 类型
        return []
    if 是路由证据(obs):                       # 闸3：壳/空结果绝不 promote
        return []
    if not _is_quality_job_bearing(...):     # 质量门：每类 artifact 一个质检员
        return []
    return [self._store(...)]                # 通过 → 生成 artifact_id + content_hash + 去重
```

**易错点 + 救命稻草**：
- `status` 必须是字面 `"succeeded"`，别的都进不来。
- `TOOL_ARTIFACT_TYPE` 只有 9 个工具映射到 4 种类型，没映射的工具永远不产出证据——加新工具时最容易漏这步。
- 空匹配报告要带 `no_candidate_satisfied_constraints` + `evaluated_candidate_count` 才能过质检（证明匹配器真的跑过、真没匹配上）。

**5.【刻意练习】**：给 `resume_tailoring_brief` 的质量门（evidence.py:241-249 调用的 `_VALIDATORS`）加一个要求"必须含 `target_artifact_id`"，然后跑 `test_evidence.py`，观察哪些用例挂。这让你理解：**改质检 = 改整个下游的完成判定**。

### 教案单元 4：验收 —— 完成门

**1.【概念锚点】**：大楼的"验收部"。"模型宣称完成"必须过四道检查，一道不过就打回 `waiting_user`。

**2.【核心目标】**：能解释 `RunCompletionPolicy.evaluate` 的四连问；能解释 refs 的 ANY 语义和 `matching_fallback`。

**3.【原理解读 (Why)】**：没有完成门，模型会用编造的结论收尾——"我完成了"谁都会说。**不这样做的灾难**：demo 看着能跑，一上线就给用户交付假的求职结论。完成门是证据驱动的纯函数，跟模型话术无关。

**4.【手把手实操 (How)】**（约 15 行）

```python
# RunCompletionPolicy.evaluate 的四连问（completion.py:242-292）
def evaluate(self, state, store):
    if state.status in ("waiting", "failed", "cancelled"):
        return state.status                          # 1. 已是终态 → 原样放行
    if not all(checker(store) for checker in needed):# 2. 每个 needed 技能 checker 都过
        return "waiting_user"                        #    否则 → 证据不足
    if not _bounded_summary(state):                  # 3. 摘要非空（截断 4000 字符）
        return "waiting_user"
    if not 解析refs(ANY语义):                         # 4. 至少一个 ref 命中 job-bearing 集合
        return "waiting_user"
    return "succeeded"
```

**易错点 + 救命稻草**：
- 第 4 步是 **ANY 不是 ALL**：refs 里指向低质量壳（路由证据）的被忽略，不构成失败。
- `matching_fallback`（completion.py:334）：需要 matching、已有候选、但模型一直没产出报告时，finalize 前**确定性调用一次**匹配工具——关键交付物由代码兜底，不押在模型行为上。

**5.【刻意练习】**：把第 4 步的 ANY 改成 ALL（要求每个 ref 都能解析），跑 `test_completion.py`，观察哪些用例开始返回 `waiting_user`。回答：为什么设计者选 ANY？（提示：真实 refs 常混着路由证据，ALL 会把"基本成功"误判成失败。）

### 教案单元 5：组装 —— CareerRunController

**1.【概念锚点】**：大楼的"总装车间"。预算、证据、完成门第一次以"一个 run"的形式协同工作——这就是可信内核。

**2.【核心目标】**：能自己写一段 `FauxScript` 序列，跑通 `controller.run` 并断言成功。

**3.【原理解读 (Why)】**：单独看每个零件都懂，但"谁先跑、谁扣预算、谁写证据、谁判成功"的顺序才是内核的价值。**不这样做的灾难**：零件各自正确，焊在一起却互相打架（预算不共享、证据不互通、完成门没接上）。

**4.【手把手实操 (How)】**（约 16 行，源自 test_controller.py:347-399 的 `test_success_single_skill`）

```python
from pi_ai import ToolCall
from pi_ai.providers.faux import FAUX_MODEL, FauxScript, push_script, clear_scripts
from pi_career_skills.runtime.controller import CareerRunController, RunRequest
# build_stub_registry 是 test_controller.py 里的 helper（桩 handler 替换真实网络工具）
from pi_career_skills.tests.test_controller import build_stub_registry

reg, _ = build_stub_registry()
controller = CareerRunController(
    FAUX_MODEL, registry=reg, get_api_key=lambda provider: "test-key")
clear_scripts()
push_script(FauxScript(tool_calls=[ToolCall(id="s1", name="delegate-job-discovery",
                                            arguments={"task_goal": "找Java岗位"})]))
push_script(FauxScript(text="已完成职位发现。"))    # 子代理收尾
push_script(FauxScript(text="已为您找到岗位。"))     # supervisor 总结
result = await controller.run(
    RunRequest(task="找Java岗位", needed_skills=("job-discovery",)))
assert result.status == "succeeded"              # 完成门说了算，不是模型说了算
```

**易错点 + 救命稻草**：
- 每个模型 turn 都要 `push_script` 一个脚本（FIFO 顺序消费）；少一个就会拿到 `FauxScript(text="faux response")` 兜底，行为错乱。
- `needed_skills` 只给一个技能，否则完成门要求全部技能都过，你没脚本它就一直 `waiting_user`。
- `get_api_key` 必须给，否则 deepseek provider 直接 `MODEL_API_KEY_MISSING` 短路（controller.py:169-174）。

**5.【刻意练习】**：把 `needed_skills` 改成 `("job-matching",)`，自己编一段脚本序列（先 discovery 出证据、再 matching 出报告），跑通后把两个技能都放进去，观察 `completed_skills` 变成两个元素。

### 教案单元 6：分工 —— Supervisor + 委托契约

**1.【概念锚点】**：大楼的"管理层"。老板（Supervisor）只派活、不干活；每个员工（技能子代理）只带自己的工具箱（10/1/1/1 个工具）。

**2.【核心目标】**：能解释"六态委托结果""传引用不传副本""前置证据门槛"三件事。

**3.【原理解读 (Why)】**：一锅烩的 agent 上下文污染是多 Agent 系统最大的坑——上个子任务的历史消息会把下个子任务带偏。**不这样做的灾难**：跨代理自由文本传参，改一个字段全链崩；下游在没证据时被委托成功，产出全是编的。

**4.【手把手实操 (How)】**（约 15 行）

```python
# ① 委托工具的参数：恰好是契约四件套（delegation_tools.py:87-130）
#   objective / input_refs / constraints / expected_output
# 每次委托 = 一个 fresh 子代理，只带自己技能的 10/1/1/1 个工具（factory.py:104-144）

# ② 前置证据门槛：模型想委托 matching，必须先有证据（controller.py:526-546）
if skill not in allowed_skills:           → DELEGATION_SKILL_NOT_ALLOWED
if skill in state.completed_skills:       → DELEGATION_SKILL_ALREADY_SUCCEEDED
if not _skill_has_evidence(skill, store): → TARGET_EVIDENCE_NOT_FOUND

# ③ 六态结果（contracts.py:13-21）：SUCCESS / PARTIAL / NEED_USER / RETRYABLE / BLOCKED / FAILED
# ④ 传引用不传副本：ArtifactRef 只有 artifact_id / source_url / content_hash / artifact_type
```

**易错点 + 救命稻草**：
- 委托参数用 `task_goal`（旧）还是 `objective`（新）决定 terminate 语义——旧的成功会结束 run，新的留在循环里（delegation_tools.py:192-195）。混用会得到诡异的行为。
- 前置门槛是**确定性校验**，模型绕不过去——这是"模型选技能、内核验票"的分工。

**5.【刻意练习】**：在 `capabilities.py` 的 `build_capability_registry` 里加第 5 个技能（先给个空 `tool_names`），观察 `_SUPERVISOR_SKILLS`（factory.py:43）自动多一个 delegate 工具。再回答：要让它真正"能完成"，还需要在哪 3 处登记？（答案：`registry.py` 工具目录、`prompts.py` 精编提示词、`_SKILL_CHECKERS` 完成检查器。）

### 教案单元 7：进化 —— 离线评测闭环

**1.【概念锚点】**：大楼的"训练场"。每次改代码先体检，防止老毛病复发（回归）。

**2.【核心目标】**：能跑 `run_chain` 和审计闸；能解释证据如何经 `seed_artifacts` 跨环节继承。

**3.【原理解读 (Why)】**：改一行提示词可能让整个系统静默退化——昨天的成功案例今天全挂。**不这样做的灾难**：没有离线回归集，每次升级都是赌命。这也是"越用越好"的第一环：先证明没变差，再谈变好。

**4.【手把手实操 (How)】**（约 15 行）

```python
# 链式评测：环节 N+1 只在 N 成功时跑（chain.py:257-306）
async def run_chain(cid, *, question_dir, out_dir, model_id, controller_factory=None):
    doc = json.loads((question_dir / f"{cid}.json").read_text(encoding="utf-8"))
    for index, link_doc in enumerate(doc["chain"], start=1):
        if index > 1 and 上一环.status != "succeeded":
            break                                     # 断链即停
        goal = link_doc["question"]
        seed_artifacts = _build_seed_artifacts(上一环)  # 证据经 seed 注入下一环
        result = await controller.run(RunRequest(task=goal, seed_artifacts=seed_artifacts))

# 确定性审计闸：评测结论不靠模型话术（audit.py:366/433/494/558）
# _audit_discovery / _audit_matching / _audit_tailoring / _audit_planning
```

**易错点 + 救命稻草**：
- `question_dir` 下每个问题是一个 `{cid}.json`，必须含 `chain` 数组，否则 `ValueError`。
- 继承证据有字节预算（`observed_public_evidence` 24KB / `structured_job_candidates` 32KB，chain.py:46-57），不是全量塞给下一环。
- 评测记录 JSON 落盘（runner.py:251）、launch manifest（cli.py:166）、源对比 markdown（compare.py:349）。

**5.【刻意练习】**：在 `question_dir` 里新建一个 `{cid}.json`，`chain` 放两个环节（"收集 AI 应用开发岗位" → "给出一份匹配排序"），跑 `run_chain`，检查 `out_dir` 里生成的记录文件，确认第二环继承到了第一环的证据。

### 反爬治理专项练习：先减少访问，再谈召回率

这是单元 3（工具）与单元 7（评测）的交叉练习：

1. 先确认来源顺序：腾讯文档/招聘台账 → 企业或高校官方页 → 公开搜索 → 商业聚合站。
2. 用 canonical URL 去重，观察相同页面不同 query 顺序和 fragment 是否只产生一次网络请求。
3. 将同站点批量抓取设置为串行，确认第二个请求遵守间隔；模拟 `anti_bot_challenge` 后，确认兄弟 URL 直接进入冷却，不再次请求。
4. 对比缓存命中前后的请求数，不以“抓到更多页面”作为唯一指标，而看“每个有效 JD 的请求成本”和“反爬率”。

禁止用代理轮换、验证码破解或隐身指纹完成练习；目标是形成合规的负载控制和可观测性。

### Bug 狩猎指南（3 个最常见报错 + 反推是哪个单元没学扎实）

| 报错 / 现象 | 反推没学扎实的单元 | 第一现场查哪里 |
|---|---|---|
| `completion_evidence_unavailable`、状态 `waiting_user` | **单元 3 或 4**：证据没入库 / 质检不过（3），或完成门过不去（4） | 看 `result.events` 里 `tool_observation` 的 status 和 error_code |

| `anti_bot_challenge` / `domain_temporarily_blocked` | **反爬治理专项**：同站访问过密或来源选择不当 | 查 `request_governor` 的缓存、间隔、冷却事件；切换官方来源，不要无状态重试 |
